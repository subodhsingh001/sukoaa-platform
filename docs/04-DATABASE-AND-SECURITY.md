# Database, backend and guards

## Tables

| Table | Main columns | Access |
| --- | --- | --- |
| auth.users | id, email, provider-managed credential fields | Managed by Supabase Auth |
| profiles | id → auth.users, display_name, created_at | User reads/updates own profile |
| app_roles | user_id → auth.users, role member/admin | User reads own role; no client insert/update/delete |
| projects | id, owner_id, name, language, source, stdin, created_at, updated_at | Owner-only CRUD via RLS |
| releases | id, title, version, platform, download_url, sha256, published, created_by, created_at | Published rows public; admin manages rows |

An auth-user trigger creates a profile and member role. Project timestamps are generated by the database. An insert trigger serializes per-owner quota checks with an advisory lock and limits each owner to 100 projects. Source is limited to 50,000 characters and stdin to 5,000. Projects are loaded 50 at a time (the current UI displays the latest 50; pagination is a future enhancement).

Database migrations should be committed and applied deliberately. The supplied migration targets a new database and is not idempotent; do not rerun it on a database that already has these tables. Use a new migration for later changes. Supabase backups/restore policies depend on your chosen plan; verify and test them before relying on them.

## Authentication approach

The application calls Supabase Auth over HTTPS, verifies the access token against `/auth/v1/user`, and keeps access/refresh tokens in HttpOnly, SameSite=Lax cookies. Production cookies use Secure and the `__Host-` prefix. It never uses an unverified decoded JWT or a local cookie value as proof of identity. Access is verified before database calls. A refresh token can refresh an expired access token; rotated tokens are written back into cookies in route handlers. There is no Next.js proxy/middleware used as the sole authorization layer.

The backend sends the current user's JWT to Supabase's Data API using the publishable key. It does not use a service-role secret. RLS is essential even if the key is currently only stored server-side. Frontend role labels are never authorization. Roles are stored in app_roles, not editable signup metadata.

## Promote your admin

First sign up and confirm your account. In Supabase SQL Editor, replace the example address and run:

```sql
update public.app_roles
set role = 'admin'
where user_id = (select id from auth.users where email = 'YOUR_EMAIL');
```

Then sign in at /account and open /admin. Do not expose this SQL as a public endpoint. Demotion uses the same SQL with `role='member'`.

## Redis behavior

The limiter performs INCR and EXPIRE inside a Lua script so the increment and TTL are atomic. Keys are SHA256-hashed identifiers. The fixed window starts on the first request and allows the usual fixed-window boundary burst; it is not a sliding-window/fairness guarantee. Current API limits: auth 10/minute per trusted-IP/shared bucket; reads 60/minute/user; project writes 20/minute/user; admin 20/minute/user; remote runs 5/minute/user, 50/day/user and 100/minute globally; polling 120/minute/user. Daily windows are 24-hour windows beginning at the first request, not calendar days.

The auth limiter's anonymous key uses only the specifically configured hosting-proxy header. Otherwise it shares one conservative bucket. Never blindly trust client-controlled forwarding headers. Remote jobs expire after 300 seconds in Redis. A job ID is random, but ownership is also checked. Stop in the UI stops polling/browser execution; it does not cancel an already submitted Judge0 job, whose server limits still apply.

## Remaining security work before a public service

Run live two-account ownership tests and Redis outage/rate-limit tests. Configure SMTP and auth anti-abuse protections. Add a privacy/contact policy for actual hosting/runner vendors and retention behavior. Put untrusted previews on a dedicated sandbox origin for a broad public multi-user service; iframe/worker restrictions are useful but are not a complete DoS/memory isolation boundary. HTML/React loops can still freeze a frame/tab. Do not publish a shared arbitrary-code service based only on a same-process container boundary. Maintain dependency updates, signing, rate monitoring, provider spending limits, backups and incident response.

The website includes conservative response headers; a site-wide nonce CSP is not implemented. Production content security and CDN behavior need review on your chosen host. Supabase's direct API still needs RLS/quota/constraint protection; application route rate limits do not automatically protect direct Data API requests.

## Live tests after setup

1. Create accounts A and B and confirm both emails.
2. A saves a project. B's GET list must not contain it.
3. B attempts PATCH/DELETE of A's project ID; expect no access/not found. Also test direct Supabase REST access under B's JWT in a controlled test client.
4. An anonymous request cannot read projects or drafts of releases.
5. A member cannot POST /api/admin even if signup metadata contains `role: admin`.
6. A user cannot change app_roles through direct database API access. Run `supabase/check-rls.sql`; all role write privilege flags must be false.
7. Cross-origin POST with a valid session is rejected. Expired/forged tokens are rejected/refreshed only by Supabase.
8. Remove Redis temporarily from staging; protected production actions must return a controlled error, not silently bypass limits.
9. Delete a disposable user's test project; another user's data is unaffected. Verify backups/restore separately.
